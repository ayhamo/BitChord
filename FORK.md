# Fork changes

Everything this fork adds lives in new files where possible. This file lists every place it touches an **upstream** file, so a conflicting upstream merge can be redone by hand. Fork lines in upstream files carry a `// fork` comment (or are in a block that starts with one).

## Upstream behaviour the fork changes (owner-approved)

What a user of upstream would notice working differently, as opposed to fork features added beside it. The owner is told before any new entry lands here; each entry's hook lines are in the tables below. Kept from 2026-11-04 on.

- **Lyrics: no auto-scroll while a line is held** (phone and PC, shared `PlayerLyrics.kt`, `ForkLyricsHold`). Upstream kept following the playing line during the ~0.5 s press that starts a lyrics-card selection, so the line under the finger moved and another was picked. A quick tap-to-seek also pauses following while the finger is down.
- **Wide player layouts on the PC** (shared `LandscapePlayer.kt`, one hook line; `ForkWidePlayer`). Settings → Appearance: Classic (upstream's), Halves (default), Halves with a smaller cover. The phone keeps upstream's layout.
- **Dependent settings rows greyed instead of hidden** (phone, `SettingsSheet.kt` hooks via `forkDisabledWhen`): Crossfade while Automix is on, Synced lyrics' sub-rows, Animated cover art's sub-rows, bit-perfect / USB rows, Liquid Glass, signatures, Discord's card, ListenBrainz / Last.fm sub-rows. Upstream hid them.
- **Cover clips: a failed lookup is not remembered as "no clip"** (`CanvasRepository`, `ForkCanvasLookup`): retried after a minute, or when the provider's own backoff ends. Upstream cached every miss for the session. Spotify gets a signed-token fallback and a 5 min harvest backoff; Apple's last good token is kept as a backup.
- **YouTube's Library shelf is called "YouTube playlists"** (`LibraryScreen.kt`, `MainActivity.kt` title hook).
- **Replay genres: Last.fm's temporary errors aren't filed as "no genre"** (phone `ArtistFacts.fetchGenres`, one hook; the PC the same). A rate limit or service error inside a 2xx answer used to blank every artist heard meanwhile for 14 days; "artist not found" is still an answer.
- **YouTube's streaming token: a new session re-mints on the loaded page** (shared `PoTokenGenerator`, phone and PC; PC-Continued c310d0e3). Upstream built a new botguard page per session change; now only a failed re-mint rebuilds it, and a page still loading is adopted by the next request instead of left behind.
- **Home: repeated release shelves dropped, shelf headings open "See all"** (shared `Models.withoutRepeatsOf` 2 lines, `ForkShelfRepeats`, `ForkShelfMore`; phone and PC; Desktop Revived bbfb5a78, 367bf58e, e7affc8b, fbd0a9a0). "New music videos" no longer shows twice; a heading with YouTube's More link gets a chevron and opens the album/playlist/artist page, else a grid of the feed.
- **Home: a shelf without YouTube's See all link opens its own cards too** (shared `ForkShelfMore.forkHasMore`; phone and PC; owner, 2026-11-05): a row of 6 or more cards (not Quick picks / Listen again lists) gets the chevron and opens as the grid. Every signed-out Home shelf and the Navidrome shelves carry no link.
- **"Hide system bars"** (phone, Settings > Appearance; owner, 2026-11-06): None / All / Top / Bottom, app-wide, a swipe shows them for a moment. Upstream's "Hide status bar in player" is greyed while All or Top is picked; its end, and a music video leaving full screen, put the mode back (`ForkSystemBars.reapply`). Dialogs and sheets are their own windows, so the bars show while one is open.
- **Automix analysis JSON is written locale-safe** (`analysis_jni.cpp` `AppendNumber`, Desktop Revived 9dcd4818). No output change on the phone (same bytes as `%.6g`); only a comma-decimal C locale, not hit today, would have broken it.
- **Cover clips: fewer wasted requests, no wrong clips for non-Latin titles** (phone and PC). Spotify's forced hash refresh waits 5 min (30 after a look that found nothing new) and retries only with a new hash; a client token that won't mint is held 10 min; titles fold keeping every script's letters (`titlesMatch`); an iTunes error is not cached as "no art"; an empty community index waits 5 min as a cool-down.
- **Downloads** (phone): when Android stops the download service, its tracks fail with "Stopped by Android; tap to retry" (were stuck "Queued"); Delete download cancels that release's tracks still in flight; file names are cut by UTF-8 bytes (200); a finished file never replaces another of the same name (" (2)").
- **Playlist sync** (phone): a "New songs in X" tap approves that playlist only (upstream approved every waiting batch); the catch-up runs at most every 6 h even while one playlist keeps failing; a failed read keeps its ask.
- **Offline: AutoPlay / Start radio on a Navidrome song queue nothing** (phone `Autoplay.kt`, one line, as the PC already did): the server's songs wouldn't play.
- **Navidrome stars follow the server** (shared `LikeState.forkUpdate`, `NavidromeStars`): the server's full star list replaces the local one (a star taken off elsewhere goes here too); taps go out in order per song, the last wins, a refused one rolls back.
- **PC Settings group headings are big bold titles** (`ForkSettingsGroupTitle`, one hook in `SettingsGroup`; owner, 2026-11-06): upstream drew them as small grey all-caps labels, smaller than the rows.
- **Addon verification refusals hold until restart** (phone, `AddonAuth.session`, one value; owner asked 2026-11-06 that addon verification failures be handled properly). v1.9.1's addons can demand proof of upstream's own signed app, which this fork can never give. Upstream re-attests 15 min after a refusal (30 s after `outdated_app`), each time a hardware key and two calls to upstream's auth service; the fork keeps the refusal until the app restarts or a tester code is saved. The addon is skipped and its Sources row says why, as upstream does.
- **The released app may use http** (`app/src/prod/AndroidManifest.xml`, new; a user report, owner's call 2026-11-07): upstream's main manifest sets `usesCleartextTraffic="false"` and only its dev flavor turns it back on, so a Navidrome or WebDAV server on a LAN or Tailscale address worked in dev builds and failed in the release with "CLEARTEXT communication … not permitted". `NavidromeSettings.normalizeUrl` now gives a bare private or Tailscale IPv4 (`192.168.1.5:4533`, `100.x.y.z`) `http://` (Navidrome's own default); names and public addresses still get `https://`, a typed scheme is kept. android.yml checks every published APK allows it (`aapt2`).
- The fixes in "Upstream bugs the fork fixes" at the end of this file also change upstream behaviour, by fixing it.

## Gotchas

- Navidrome songs carry `albumId` / `artistId` set to the library's own album and artist pages (`LocalGroups` ids). That is what keeps the player from asking YouTube for "links" about a song it has never heard of, and it makes the player's album and artist taps open the library pages. No upstream hook needed.

- Stream and cover URLs send Subsonic's `v` parameter as `%76`. The player treats any URI with a `v` query parameter as a YouTube watch link, so a literal `v=1.16.1` made every Navidrome song fail ("URL not accepted: https://www.youtube.com/watch?v=1.16.1"). Navidrome decodes the key and still reads it.

## Upstream bugs the fork fixes

Worth sending upstream, and worth checking at each merge whether upstream fixed them its own way (then drop the fork lines):

- PC `DesktopCanvasVideo`/`DesktopCanvasView`: an HLS cover clip (Apple Music) was streamed by FFmpeg while it played, reading at the frame rate and not at all while paused; the CDN closed the half-read connection and the clip broke into `Invalid NAL unit size` errors after a few seconds, and every loop pass refetched it (`ForkClipSource`).
- `MainActivity.playDetailSongs()`: tapping a song on an album/playlist page queued the page's running order whatever the sort (A–Z, date, …), so Next didn't follow what the page shows.
- `AudioCache.prefetchQueue()`: WebDAV/SMB ids were warmed as YouTube ids (wasted lookups).
- `StreamResolver.signatureTimestamp()`: NewPipe wasn't initialised when no YouTube stream had been resolved yet, so the YouTube history couldn't register.
- `PlaylistSync`: one "New songs in X" tap approved every playlist's waiting batch; a failed read cleared its ask; one playlist that always failed kept every check incomplete, so each app open re-read every followed playlist.
- `Downloads.deleteCollection`: tracks still queued or running kept downloading after the delete and came back with nothing listing them.
- `Downloads.onStopped`: when Android ended the download service (Android 15+'s data-sync budget), its tracks stayed "Queued" in `pending` for good and a re-tap did nothing.
- `DownloadStore`: two tracks with the same file name finishing at once, the second rename replaced the first's file; the 255 limit is bytes, so a long CJK title failed to download at all.
- `SpotifyCanvasQuery.canvasHash(forceRefresh)`: with a stale hash every song re-scraped open.spotify.com and its script bundles (several MB); `SpotifyToken.clientToken` asked a refusing endpoint again for every request (~5 POSTs a song).
- Canvas title matching (`normalizeForMatch`, phone and PC providers): only a-z0-9 kept, so a non-Latin title folded to "" and matched any other title by the same artist (another song's clip; Apple's `contains("")` scored it).
- `AppleCatalogue.sharesTitles`: an HTTP error or iTunes rate limit answered "no", which the callers cached as "Apple has no art for this artist" until a restart.
- `CommunityCanvas.manifest`: with an empty index (host down) every lookup fetched it again, one request per song.
- `PlaybackService.startBoundedContext`: a new album/playlist carried the previous song's AutoPlay tail (`existingAutoplay`), so it never got a radio of its own. Upstream fixed it the same way in v1.9.1 (and also clears the repeat-all stash); the fork's line is gone.
